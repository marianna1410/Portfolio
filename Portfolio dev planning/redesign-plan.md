# Portfolio Redesign — план дій по сесіях

Цей файл — для тебе, Mary: як розбити редизайн на керовані шматки, у якому порядку і як запускати кожну сесію Claude Code. Технічна конкретика (кольори, node-ID, асети, анімації) — у сусідньому файлі **`redesign-brief.md`**, який ти тримаєш у репозиторії й на який посилаєшся в кожній сесії.

## Оцінка масштабу

Редизайн **сконцентрований**, не тотальний. Змінюється переважно головна сторінка та спільні компоненти; кейси майже не чіпаються.

| Область | Обсяг | Чому |
|---|---|---|
| Токени (кольори + 2 радіуси) | 🟢 Малий | Дельта готова у brief; механічна заміна значень. |
| Спільні компоненти (хедер, футер, дропдаун, лого, теги) | 🟡 Середній | Темний хедер/футер + copy-email + київський час. Оновлюються 1 раз, діють усюди. |
| Головна: Hero + анімація | 🔴 Великий | Новий концепт + найскладніша анімація (typewriter + skeleton + reveal). |
| Головна: Experience + Banner + Behind the Screen | 🔴 Великий | Нова секція-банер із чат-анімацією + перебудований блок із плеєром і фолдерами. |
| Головна: Works | 🟢 Малий | Колір фону, пігулки-теги, темні зображення. |
| Кейси (Lucida + Vaia) | 🟢 Малий | Головні зображення, next-case, теги, мобільний TOC. Тіло не чіпаємо. |
| Мобілка/таблет + доступність + QA + деплой | 🟡 Середній | Проходить по всьому за `mobile-adaptation` і чек-листом a11y. |

**Разом: ~6 сесій.** Одна сесія Claude Code = одне «вікно контексту». Тримати кожну сесію в межах одного зв'язного шматка, щоб Claude не губив контекст і ти могла перевірити результат порційно.

---

## Принцип розподілу (чому саме такий порядок)

1. **Фундамент → спільне → сторінки → анімації → QER.** Спочатку токени, бо на них тримається все. Потім спільні компоненти (хедер/футер) — вони на **кожній** сторінці, тож оновивши їх раз, ти одразу бачиш зміну всюди. Далі — головна секція за секцією. Кейси наприкінці, бо вони переважно успадковують уже готове спільне.
2. **Структура і її анімація — в одній сесії.** Hero-розкладку й Hero-анімацію робимо разом, бо вони пов'язані (картки з'являються як частина анімації). Так само банер.
3. **Найважче — не першим і не останнім.** Hero-анімація складна; робимо її, коли фундамент і хедер уже стабільні, але поки є запас уваги.
4. **Перевірка після кожної сесії.** Не «подивлюсь у кінці», а звіряєш кожну сесію з відповідним фреймом Figma (node-ID у brief) одразу.

## Реліз через гілку (щоб усе вийшло одразу)

Мета: сайт має перемкнутися зі старого на новий **весь одночасно**, а не шматками. Тому вся робота йде на окремій гілці, а прод чіпаємо лише в самому кінці.

**Хостинг: Vercel.** Vercel підключений до GitHub і працює так: на **кожну гілку** він автоматично робить окреме тимчасове **прев'ю-посилання**, а **прод** оновлює тільки з основної гілки (`main`). Це рівно те, що потрібно.

Порядок:

1. **Перед Сесією 0** Claude Code створює гілку `redesign` від `main`. Прод із цієї миті недоторканий.
2. **Кожна сесія** комітить і пушить у `redesign`. Vercel автоматично оновлює **прев'ю-посилання** цієї гілки — там ти дивишся новий сайт наживо. Публічний сайт увесь цей час старий.
3. Порційні коміти = точки збереження всередині гілки. Можна відкотити будь-яку сесію, прод не постраждає.
4. **Наприкінці** (після Сесії 5 і повної перевірки) — відкрити Pull Request `redesign → main`, востаннє глянути прев'ю, і **злити (merge)**. Vercel одразу задеплоїть `main` у прод — сайт оновлюється **весь одразу**, цілісно.

Тобі не треба вводити git-команди руками — Claude Code створює гілку, комітить і зливає сам. Твоя роль: дивитись прев'ю-посилання після кожної сесії і сказати «зливаємо» в кінці. Прев'ю-URL Vercel показує у себе в дашборді (і в коментарі до Pull Request на GitHub).

> Порада: не мерж, поки не пройдено «Definition of Done» (brief §10). Один фінальний перегляд прев'ю на десктопі й телефоні — і тоді merge.

## Як запускати кожну сесію

1. Поклади `redesign-brief.md` (і старі spec-файли) у репозиторій — хай Claude Code має їх під рукою.
2. На старті сесії скажи приблизно: *«Читаємо `redesign-brief.md`. Робимо Сесію N — [назва]. Дотримуйся залізних правил (§1): асети з папки, не з Figma; типографіку й відступи не чіпати; кожне значення — з джерела. node-ID секцій бери з brief і читай макет через Figma MCP.»*
3. Наприкінці сесії попроси **короткий підсумок змін** і сам(а) звір з відповідним фреймом Figma.
4. Уся робота — на гілці `redesign` (див. «Реліз через гілку»). Комітьте порційно всередині неї, щоб легко відкотити; прод не чіпаємо до фінального merge.

## Де тримати руку на пульсі

- **Hero-анімація (Сесія 2)** — найтонше місце; закладай, що доведеться підкрутити «по відчуттях» (швидкість друку, тривалість skeleton).

- **Асети** — якщо Claude чогось не знаходить, він має **попросити список/додати**, а не тягнути з Figma.
